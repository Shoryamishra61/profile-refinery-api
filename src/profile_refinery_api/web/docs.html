Start here

Two ways to extract

A / REQUEST-SCOPED

Bring an authorized session per call

Best for the public extraction desk or your own backend. Credentials live only inside one transient runtime. No Profile Refinery API key is required.

POST /v1/session-extractions
B / OPERATOR

Use a server-configured session

Best for a controlled deployment. LinkedIn cookies stay in deployment secrets and callers authenticate with a separate product API key.

GET /v1/profiles?url=…

    "urls": ["https://www.linkedin.com/in/example/"],

      "user_agent": "<session-user-agent>",
      "accept_language": "en-US,en;q=0.9"

  }'

03

Session envelope

Authentication has two distinct layers

01 / LINKEDIN

li_at

Primary authenticated session

The most sensitive value. Submit the cookie value only, never the `li_at=` prefix.

02 / CSRF

JSESSIONID

Cookie-to-header binding

Must come from the same session. The transport strips optional quotes and derives the matching csrf-token.

03 / CONTEXT

bcookie

Optional browser identifier

Useful ordinary session context, but not authentication. The web desk asks for this companion value only.

04 / CALLER

X-API-Key

Profile Refinery operator key

Protects operator and batch routes. It is unrelated to LinkedIn and is not needed by the request-scoped route.

WHY DUPLICATES ARE REJECTED

Never repeat li_at or JSESSIONID inside companion_cookies. Conflicting authoritative cookies make session behavior ambiguous; a duplicate JSESSIONID can desynchronize the cookie from the CSRF header.

05

Curated route catalog

Endpoints by operational intent

GET/v1/profiles?url={linkedin_url}Operator single profile

Uses the server-configured session and requires X-API-Key.

POST/v1/session-extractionsRequest-scoped extraction

Accepts 1–10 URLs and an authorized transient session; returns one explicit result per URL.

POST/v1/link-discoveryLocal file and text discovery

Finds member/post URLs in TXT, CSV, JSON, XLSX, DOCX, and PDF without contacting LinkedIn.

POST/v1/batchesOperator batch workflow

Creates deterministic, journaled jobs with bounded extraction and partial-failure isolation.

GET/v1/batches/{batch_id}/exportStructured export

Returns JSON, CSV, or XLSX with formula-safe cells and no-store cache policy.

GET/healthz · /readyz · /v1/capabilityOperational state

Separates process liveness from observed live-extraction capability and circuit state.

Schema 1.2.0

Every field carries meaning about absence

A value is never returned alone. Each field includes an availability status and provenance describing its source operation, observation time, parser version, and optional entity reference.

08

Research discipline

Three evidence classes. Never interchangeable.

LIVE

Current authorized HTTP observation

The only class that establishes present upstream behavior and deployed extraction success.

REAL_HAR_REPLAY

Deterministic real-capture replay

Proves decoding and normalization against a captured response, not current availability.

SYNTHETIC_UNIT

Authored mutation and boundary input

Proves controlled behavior under known shapes. It can never support a live-data claim.

HTTP 200 alone is not evidence of a profile. Core success requires a usable target identity; optional section success requires a semantic parser result. No LLM fills missing fields.

09

Production behavior

Liveness is not readiness

/healthzProcess responds

Always reports application liveness. It makes no claim about LinkedIn.

/readyzExtraction capability

Requires session configuration, a closed breaker, and a successful normalized live observation in this process.

/v1/capabilityControl-plane state

Exposes safe governor, breaker, and queue information without credentials or payload bodies.

BOUNDARY

No automated login, browser automation, CAPTCHA solving, account rotation, proxy rotation, fingerprint spoofing, or access-control circumvention. Challenges are terminal and open the circuit breaker.
